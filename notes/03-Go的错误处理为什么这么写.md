# Go 的错误处理为什么这么写

- 一句话定位：Go 把错误当**普通返回值**，`if err != nil` 写满整屏不是代码丑，
  而是这门语言在用显式控制流换"谁都不能假装没出错"。
- 配套示例：`syntax/09_error`（哨兵错误、`errors.As`、`%w`、`panic/recover`）

## 1. 和 Java 的 try/catch/finally 对照

```java
// Java：错误从调用点"飞"走，正常路径和异常路径混在一个 try 里
try {
    Config c = load(path);
    return parse(c);
} catch (IOException e) { throw new RuntimeException(e); } finally { close(); }
```

```go
// Go：错误沿返回值一格一格往上传，每一步都看得见
c, err := load(path)
if err != nil { return nil, fmt.Errorf("加载配置失败: %w", err) }
defer c.Close() // 相当于 finally，但写在成功之后、业务之前
return parse(c)
```

差异不在语法糖，而在**错误是控制流还是数据**：Java 的异常是非局部跳转，调用方可以一路
不写 catch 让它穿过去；Go 的错误就是 `error` 值，想忽略必须显式写 `_`，代价是重复的
`if err != nil` ——这是设计取舍，不是需要"优化"掉的东西。

## 2. 哨兵错误与 errors.Is

```go
var ErrNotFound = errors.New("not found") // 哨兵错误，包级导出
if errors.Is(err, ErrNotFound) { ... }    // 正确
if err == ErrNotFound { ... }             // 错误：包装后必失效
```

一旦中间有人写了 `fmt.Errorf("...: %w", err)`，`err` 就是那层包装对象，`==` 必然 false。
`errors.Is` 会沿包装链一路 `Unwrap`，任何一层命中就返回 true。哨兵错误适合"调用方需要
按情况分支"的场景，`io.EOF` 就是最好的例子。

## 3. 自定义错误类型与 errors.As

需要携带结构化信息（字段名、行号、重试次数）时定义一个实现 `error` 的类型，并给它
`Unwrap() error` 以便穿透包装层（完整定义在第 6 节）。取值靠 `errors.As`：

```go
var ce *ConfigError
if errors.As(err, &ce) { // 第二个参数必须是目标类型变量的地址
	fmt.Println("字段是:", ce.Field)
}
```

记忆点：**`Is` 判"是不是某个错误值"，`As` 取"是不是某个错误类型"**。
`%w` 与 `%v` 的区别也和它俩有关：`fmt.Errorf("读取配置失败: %v", err)` 只留下字符串、
链条断了，`%w` 才生成包装错误、可继续 `Is`/`As`。规则是**一个错误只用一次 `%w`，
且用在你能判断语义的那一层**；别为了"能 Unwrap"到处 `%w`，错误链会失控。

## 4. panic/recover 的边界

业务错误一律 `return err`；`panic` 只留给"继续跑没有意义"的场合：启动时配置缺失、
不可恢复的内部状态不一致。`panic` 会先执行当前 goroutine 的 `defer`，所以在最外层用
一处 `defer + recover` 兜住并转成错误返回，是合法且常见的边界写法（本仓库约定业务代码不写 `panic`）。

## 5. 可运行的复现代码

整段粘进 `main.go` 后 `go run .`：

```go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("not found")

type ConfigError struct {
	Field string
	Err   error
}

func (e *ConfigError) Error() string { return "配置项 " + e.Field + ": " + e.Err.Error() }
func (e *ConfigError) Unwrap() error { return e.Err }

func load(field string) (int, error) {
	if field == "" {
		return 0, fmt.Errorf("load: %w", ErrNotFound)
	}
	if field == "bad" {
		return 0, &ConfigError{Field: field, Err: errors.New("格式错误")}
	}
	return 42, nil
}

// guard 是最外层唯一该出现的 recover：把 panic 转成错误返回。
func guard(fn func()) (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("panic 被兜住: %v", r)
		}
	}()
	fn()
	return nil
}

func main() {
	if _, err := load(""); errors.Is(err, ErrNotFound) {
		fmt.Println("命中哨兵错误:", err)
	}
	var ce *ConfigError
	if _, err := load("bad"); errors.As(err, &ce) {
		fmt.Println("取出结构体:", ce.Field)
	}
	fmt.Println("recover:", guard(func() { panic("不该继续了") }))
	raw := fmt.Errorf("外层: %v", fmt.Errorf("内层: %w", ErrNotFound))
	fmt.Println("用 %v 后还认得出吗:", errors.Is(raw, ErrNotFound)) // false
}
```

## 一句话结论

Go 用**返回值 + 显式 `if err != nil`** 取代异常：判断错误用 `errors.Is`/`errors.As`
（`==` 在包装后必失效），传递上下文用 `%w`，`panic/recover` 只当"程序不该继续"的最后边界。

## 我踩过的坑

- 中间层写 `fmt.Errorf("...: %v", err)` 图省事，上游 `errors.Is` 永远 false，靠打日志才发现链条被自己掐断。
- 以为 `err == ErrNotFound` 也行，直到有人给错误加了一层包装，判断集体失效。
- `errors.As(err, ce)` 忘了传 `&ce` 编译不过；还得 `var ce *ConfigError` 再取地址。
- 业务函数里到处 `recover` 想"让服务别崩"，结果把 bug 吞成静默错误返回，线上更难定位。
