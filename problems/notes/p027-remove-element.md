# 27. 移除元素

- 难度 / 类型：简单 · 双指针（快慢指针）/ 原地数组
- 思路（一句话）：慢指针 `k` 是下一个待写位置，快指针 `i` 扫一遍，`nums[i] != val` 就写进 `nums[k]` 并让 `k` 前进，等于 `val` 的直接跳过被后面的元素覆盖。
- 复杂度：时间 O(n)，空间 O(1)
- 卡点：`k` 初值写成 1（从 26 题搬过来惯性太大）会白白多留首个元素；判断条件写反成 `== val` 会把该删的全留下。另外返回值是 `k` 而不是 `len(nums)`——题目只保证 `nums[:k]` 里没有 `val`，`k` 以后是垃圾数据，断言整条切片必挂。
- Go 注意点：`nums[k] = nums[i]` 里 `k <= i` 恒成立，所以原地覆盖不会踩掉未读元素，不用额外数组。切片传参是描述符拷贝，函数内改元素调用方可见、重新赋值 `nums = ...` 则不可见。测试里 `append([]int(nil), tt.nums...)` 拷一份再跑，避免子测试共享底层数组互相污染。
- 关键代码片段：

```go
k := 0
for i := 0; i < len(nums); i++ {
	if nums[i] != val {
		nums[k] = nums[i]
		k++
	}
}
return k
```

## 我的卡点（2026/9/23，第一遍自己写的时候）

- **做法**：`num1 := nums[:0]` + `append(num1, v)` —— 这是"快慢指针"的 **Go 惯用写法**：把 `nums` 的前面几格当成写缓冲区，遍历时把不等于 `val` 的值写回去，最后 `return len(num1)`。**时间 O(n) / 空间 O(1)**。（练习代码在 `playground/p027_remove_element/main.go`；上面参考解用的是显式下标 `nums[k] = nums[i]`，两者等价。）
- **卡点①（最关键的一条认知）**：我一开始以为"`append` 就是在给切片扩容" —— **错**。这里 `cap(nums[:0]) == cap(nums) ≥ len(nums)`，而保留的元素最多 `len(nums)` 个 ⇒ **len 永远不到 cap ⇒ append 一次都不扩容**，全程在原数组里写。**这正是它 O(1) 空间的原因**（不是"扩容"，是"不扩容"）。验证方式：调用后打印 `nums` 全量，能看到 `[2 2 2 3]`——写进去的东西落在了 `nums` 自己的底层数组里。
- **卡点②（和题 26 的对照，这两题一起打通）**：慢指针/写指针的**初值 = "不用比较就已经确定保留的元素个数"**。
  - 题 26：数组有序 ⇒ **首元素天然唯一、一定保留** ⇒ 初值 **1**；
  - 题 27：没有元素天然保留（第一个元素也可能等于 `val`）⇒ 初值 **0**；而 `nums[:0]` 天然就表达了"保留 0 个"，所以不用手写初值，也没有 26 那个"写成 0 就把首元素覆盖掉"的坑。
- **卡点③（复杂度要对约束算）**：我曾以为"双循环 O(n²) 过不了" —— 但本题 `n ≤ 100`，n² = 10⁴ 次操作秒过。**判断会不会超时要看 n 的量级**：10² → n² 随便过；10⁴ → 5×10⁷ 能过；10⁵ → 5×10⁹ 才会超时。所以放弃双循环的理由是"不是最优解 + 易错"，不是"过不了"。
- **卡点④（返回值）**：返回 `len(num1)`（= k），**不要返回 `len(nums)`**——`k` 之后是垃圾数据，题目只保证 `nums[:k]` 里没有 `val`。
- **空数组天然安全**：`nil[:0]` / `[]int{}[:0]` 都合法，循环不执行，返回 0，不会 panic（本题约束允许 `len == 0`，我不需要额外 guard；26 那种 `k := 1` 的写法就必须加）。
- **边界实跑结果（12/12 全过）**：示例1 / 示例2 / 空切片 / nil 切片 / 单元素命中 / 单元素未命中 / 全等于 val / 全不等于 val / val 不在数组 / 首尾都命中 / 交替命中 / 全是 0；另加 n=100 上限（每 3 个含一个 1 → k=67）。
- **我在写验证脚本时踩的坑（留档）**：`reflect.DeepEqual(nil切片, []int{})` 返回 **false** ⇒ 比"空切片"时不能用深比较，要按"长度 + 逐元素"比（参考 `problems/README.md` 里记录的 p026 同类坑）。
